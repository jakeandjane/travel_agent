01

概述

1.1 特性背景与痛点

用户规划一次多日旅行，通常需要在多个 App 间反复切换（查景点、查天气、订酒店、找餐厅），再手动拼装成行程，耗时以小时计。若直接使用通用大语言模型生成行程，存在三类系统性缺陷：

痛点表现根因
幻觉严重编造不存在的景点、餐厅、票价、营业状态模型无实时数据源，靠训练记忆补全
工具调用不可靠模型把工具调用当普通文本输出，工具从未真正执行非原生工具调用协议，靠文本约定"碰运气"
体验不可信生成过程黑盒等待 60s+、失败时静默返回编造数据无真实进度反馈、无显式失败机制

1.2 特性价值

价值点说明
数据真实景点/天气/酒店/餐厅全部来自高德真实数据，每项可验证
响应快速4 路并行搜索将查询阶段从约 60s 压缩至 15s 量级
过程可信SSE 真实进度事件驱动前端展示，失败显式分层报错，杜绝"假进度、假数据"
结果可控支持 AI 微调（只改用户要求的部分）、手动编辑、历史回溯、图片/PDF 导出

1.3 特性范围

范围内：中国大陆城市的多日旅行计划生成与微调（依赖高德数据覆盖）；Web 端全流程。

范围外：酒店/门票预订与支付、账号体系（本期以 user_id 标识，无鉴权）、移动端 App、海外城市、多语言。

1.4 约束条件

  1. 外部服务仅依赖三项：DeepSeek 大模型 API、高德开放平台 API、Unsplash 图片搜索（可选，不可用时前端降级）。
  2. 核心链路部署仅需两个 API Key（高德 + DeepSeek），配置全部外置于 .env，代码中不硬编码密钥。
  3. 技术栈既定：后端 Python/FastAPI + HelloAgents 框架，前端 Vue 3 + TypeScript + Ant Design Vue + Vite。
  4. 单机单进程部署形态（本期不做分布式）。

需求分析

2.1 用户故事（INVEST）

编号用户故事价值独立性可测试性
US1作为旅行者，我输入目的地、日期、偏好，就能得到一份含时间安排、三餐、酒店、天气、预算的完整计划核心价值独立生成计划 JSON 通过 Schema 校验且数据可溯源

US6作为回头客，系统记得我的偏好（饮食禁忌/预算/已去城市），再次规划更贴合个性化价值独立二次规划请求中注入画像信息

2.4 验收准则（对应 NFR 的度量口径）

  • 查询阶段 ≤15s：以 4 个搜索 Agent 全部返回为准（日志时间戳测量，缓存命中除外）。
  • 规划成功率 ≥95%：连续 20 次端到端规划，成功 ≥19 次（成功 = 返回通过 Schema 校验的完整 TripPlan）。
  • 静默失败 = 0：3 类故障注入场景（LLM 返回非 JSON / 高德超时 / 单 Agent 失败）均须产生显式错误提示或降级标注，不得返回看似正常的假数据。

3.4 关键设计决策与权衡（ADR）

#决策点备选方案决策理由
ADR1工具调用协议A. SimpleAgent 文本约定 + 正则解析；B. FunctionCallAgent 原生 function callingB方案 A 依赖模型输出格式巧合，工具调用不可靠；B 由模型服务端保证调用协议，可靠性从"碰运气"提升为"确定性"。
ADR2高德集成方式A. MCP 子进程协议；B. 直连 HTTP 封装B方案 A 引入 uvx 外部依赖，且存在依赖缺失时静默展开为 0 个工具的故障模式（见 06.1 风险识别）；B 零外部依赖、启动开销从秒级降至 0.1s 量级、故障模式显式可控。
ADR3搜索执行方式A. 串行逐 Agent；B. asyncio.gather + to_thread 真并行B4 路搜索无数据依赖，串行是纯浪费；B 将查询阶段从约 60s 压缩至最慢单路耗时（约 15s）。
ADR4失败处理策略A. 静默返回兜底假数据；B. 显式分层异常B假数据破坏用户信任根基；B 以 503/502/500 分层表达"服务不可用/数据错误/内部错误"，前端针对性提示。
ADR5进度反馈A. 前端定时器假进度条；B. SSE 后端真实事件B假进度条与真实状态脱节，进度先到 90% 再失败是信任事故；B 的进度永远与后端阶段一致。
ADR6数据清洗A. 原始数据直接拼提示词；B. 清洗层（JSON 提取→结构化 top10→降级截断）B原始数据冗长且结构混乱，挤占上下文并降低规划质量；B 保证"垃圾不进入提示词"。
ADR7历史计划复用A. 直接复用旧计划；B. 相似度匹配注入结构参考 + 强制使用新数据B直接复用会输出过期数据；B 以打分（同城+50/偏好重叠+15/天数相近+10，阈值≥50，跨城市直接跳过）控制参考质量，并注入防照搬约束。
ADR8微调交互A. 一次性完整修改；B. 两阶段：30s 快速建议 → 用户确认 → 90s 工具执行B完整修改 90s 的"未知等待"体验差且不可逆；B 把等待拆为"短感知+用户控制权"，且建议阶段纯 LLM 无工具开销。
ADR9画像与个性化A. 无状态；B. 画像持久化 + 规划期注入BB 以极低成本（JSON 文件 + 提示词注入）获得"记得用户"的能力，复用成本低于重生成。

4.2 错误码规范（分层语义）

状态码触发类型语义前端呈现
503RuntimeError上游服务不可用（超时/网络/依赖故障）"服务暂时不可用，请稍后重试"
502ValueError数据错误（LLM 输出解析失败/格式非法）"生成结果校验失败，请重试"
500Exception未预期内部错误"服务器内部错误"
404—plan_id 不存在"计划不存在"
422Pydantic 校验失败请求体非法（天数越界/日期格式错误）字段级提示

设计约束：任何失败不得静默吞掉后返回假数据；错误信息向上逐层传递，最终由前端显式呈现。

4.3 SSE 事件协议

媒体类型 text/event-stream，事件格式 event: 类型\n data: JSON\n\n。

事件触发时机data 载荷前端状态
query_start4 路搜索开始{message, timestamp}第 1 步（进度 10%）
query_complete4 路搜索全部完成{message, timestamp}第 2 步（进度 40%）
planning_start规划 Agent 开始{message, timestamp}第 2 步持续
plan_complete计划校验并落盘{message, plan_id, timestamp}第 3 步完成（100%）
error任一阶段失败{message}错误提示 + 停止

前端消费方式：fetch + ReadableStream + TextDecoder 逐块解析（SSE 为 POST 请求，不能用 EventSource，实现于 frontend/src/services/api.ts）。

数据结构设计

5.1 核心模型（Pydantic，app/models/schemas.py）

TripRequest（请求）：city(str) · start_date/end_date(date) · travel_days(int, 1-30) · transportation(str) · accommodation(str) · preferences(list[str]) · free_text_input(str) · user_id(str)

TripPlan（计划根对象）：city · start_date · end_date · days(list[DayPlan]) · weather_info(list[WeatherInfo]) · overall_suggestions(str) · budget(Budget)

DayPlan（单日）：day_index(int) · date · description · transportation · accommodation · hotel(Hotel) · attractions(list[Attraction]) · meals(list[Meal])

Attraction（景点）：name · address · location{longitude, latitude} · rating · visit_duration(分钟) · time_start(HH:MM) · description · photos(list[str]) · poi_id · ticket_price

Meal（餐饮）：type(breakfast/lunch/dinner/snack) · name · address · time_start · estimated_cost · rating · description

Hotel（酒店）：name · address · type · price_range · rating · estimated_cost

WeatherInfo（天气）：date · day_weather · day_temp · night_weather · night_temp · wind_direction · wind_power（温度字段带校验器自动剥离"°C"）

Budget（预算）：total_attractions · total_hotels · total_meals · total_transportation · total

5.2 持久化模型

PlanRecord（app/memory/plan_store.py）：plan_id(uuid4 hex 前 8 位，形如 plan_xxxxxxxx) · user_id · created_at · city · travel_days · preferences · request(原始 TripRequest dict) · plan(TripPlan dict)

UserProfile（app/memory/user_profile.py）：dietary_restrictions · travel_style · budget_level · visited_cities(list) · preferred_activities(list) · accommodation_preference

5.3 存储设计

项目设计
介质本地 JSON 文件（UTF-8，缩进 2，可读可检）
目录data/plans/plan_{plan_id}.json；data/profiles/{user_id}.json
缓存进程内内存字典（读命中免磁盘 IO）；计划缓存 TTL 600s
写路径写文件 + 更新内存缓存双写；微调后以新 plan_id 另存（原计划不可变）
读路径缓存优先 → 文件读取
演进数据访问收敛于 PlanStore/ProfileManager 两个类，后续迁移 SQLite/Redis 仅改这两个实现

5.4 前后端类型对齐

前端 frontend/src/types/index.ts 的 TS 接口与 Pydantic 模型一一对应（含 time_start/photos/poi_id/image_url 等字段），后端 Schema 变更必须同步修改该文件并保持字段名严格一致（snake_case）。

06

DFX 设计

6.1 可靠性设计

风险识别 → 设计约束（每条约束均为对特定故障模式的前置设计）：

风险识别（故障模式）设计约束
文本约定式工具调用，模型输出格式漂移即失效工具调用一律走 FunctionCallAgent 原生协议，禁止文本拼接式调用
子进程方式集成工具，依赖缺失时静默展开为 0 个工具工具集成采用直连 HTTP，禁止子进程方案（ADR2）
同步阻塞调用，单路慢则全体慢搜索一律 asyncio.gather 并行，单路失败不阻塞其余路
失败静默返回兜底数据，用户对故障无感知分层异常（503/502/500）+ 前端显式提示，禁止假数据兜底
LLM 输出格式不稳定三重防御：严格 JSON 格式约束提示词 → 多模式提取（```json/裸 {}）→ Pydantic 校验失败则整体重试（上限 3 次）

6.2 可维护性设计

  • 静态工具注册表（tools/registry.py + amap_tools.py/llm_tools.py）：工具清单查询接口返回静态定义，不实例化 Agent、不触发外部调用——保证"看清单"操作零副作用、零耗时。
  • 配置外置：全部密钥/模型名/超时/端口经 config.py 从 .env 加载（支持加载父目录 HelloAgents 公共配置），代码零硬编码。
  • 模块边界：工具层（无框架感知）→ Agent 层（无 HTTP 感知）→ 服务层（无路由感知）→ API 层（无业务逻辑）→ 前端层；跨层仅通过 Pydantic/TS 类型通信。
  • 启动自检：服务启动时校验配置完整性并打印关键配置（密钥脱敏）。

6.3 安全性设计

  • API Key 仅存后端 .env，不入库、不进前端、日志脱敏；前端地图使用独立的 Web 端 JS Key。
  • Pydantic 输入校验覆盖所有请求体：天数 1-30、日期格式、枚举餐次等；非法输入由框架统一返回 422。
  • CORS 白名单仅放行前端开发源（localhost:5173/3000）。
  • 已知限制：本期无鉴权（见第 09 章），user_id 由前端生成（user_ + 时间戳36进制 + 随机数，localStorage 持久化）。

6.4 性能设计

  • 并行：4 路搜索并行（asyncio.gather + asyncio.to_thread 规避 Agent 同步阻塞）；单路失败不阻塞其余路。
  • 缓存：搜索结果 600s TTL 内存缓存，热点城市重复查询直接命中。
  • 数据裁剪：清洗层将 POI 统一裁剪为 top 10 简化字段，控制提示词体积；微调建议只传计划摘要而非全量 JSON。
  • 时间预算：查询 ≤15s / 规划 ≤120s / 建议 ≤30s / 应用 ≤90s，各阶段独立超时，超时即显式失败而非无限等待。
  • 已知瓶颈：规划阶段耗时由输出 token 解码主导（约 3000 token），已通过提示词精简 + 预算字段聚合控制输出规模，后续可评估流式输出规划结果（见 09.1 R7）。

6.5 易用性设计

  • 真实进度：SSE 4 事件驱动三步进度指示（10%→40%→100%）+ 脉冲动画，进度与后端阶段强一致。
  • 用户控制权：微调"建议 → 用户确认 → 应用"两阶段，确认前系统不产生任何修改；前端区分 pending（待用户操作）与 applying（执行中）状态，防止重复点击。
  • 编辑回滚：进入编辑模式时深拷贝快照，取消编辑可完整还原。
  • 降级可见：图片加载失败展示"图片加载失败"占位；地图加载失败仅记录日志不影响其他内容。

6.6 可扩展性设计

  • 工具扩展：新增高德能力 = 在 amap_direct.py 增加一个 @tool_action 方法，Agent 与其余各层自动获得该能力。
  • Agent 扩展：新增搜索维度 = 在规划服务中增加一个 FunctionCallAgent + 一行 gather 配置。
  • 模型演进：模型名/BaseURL 配置化，OpenAI 兼容协议使模型替换（如换其他厂商）无需改代码。
  • Schema 演进：Pydantic 向后兼容字段扩展 + 前端 TS 同步对齐流程（见 5.4）。

6.7 可测试性设计

风险与依赖

9.1 技术风险

#风险影响等级规避/缓解措施
R1LLM 输出格式漂移（非 JSON/缺字段）规划失败高三重防御（严格格式约束 + 多模式提取 + Pydantic 校验）+ 重试 3 次（6.1）
R2高德限流/欠费、DeepSeek 排队查询/规划超时高15s 请求超时 + 600s 缓存 + 降级标注 + 分层异常显式报错
R3Unsplash 图片源不可用景点卡片无图中前端 SVG 渐变占位图降级，不影响核心功能
R4JSON 文件并发读写数据覆盖/损坏中写路径收敛于 PlanStore 单点；微调另存新 plan_id 不覆写；演进：SQLite 事务
R5内存缓存随进程重启失效、多进程不共享命中率下降低缓存仅作加速层（数据源仍为文件/API）；演进：Redis
R6单点部署无鉴权被滥用中本期以 user_id 隔离数据；演进：接入鉴权与配额
R7规划阶段解码耗时主导（60-120s 量级）总耗时体验中提示词精简 + 输出规模控制 + 两阶段微调隔离；演进：规划结果流式输出

依赖用途故障影响面备用方案

9.3 已知限制

  1. 无鉴权：接口可被任意调用（本地/内网场景可接受，公网部署前必须补齐，见 R6）。
  2. 单轮微调：微调结果不能再基于新结果连续追加修改（可对最新 plan_id 重新发起，但无对话历史上下文）。
  3. 前端硬编码后端地址：frontend/src/views/Result.vue 中景点图片请求硬编码 http://localhost:8000（未走 Vite 代理），部署到其他环境需同步修改（列入技术债清理清单）。
  4. 自动化测试覆盖不足：当前为手动脚本 + 用例库形态，pytest 自动化按 7.5 计划补齐。
  5. 单机形态：存储与缓存均为单进程方案，横向扩展需先完成 SQLite/Redis 演进。
